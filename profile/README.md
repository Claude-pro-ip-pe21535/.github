<p>批量开号这件事，坏就坏在节奏上：前三天一切正常，第四天开始有号登录要验证，第七天集中掉一批，回头查才发现整批落在同一个机房段。这类问题不是"选错了服务商"这么简单，而是测试时间轴拉得太短。下面按 Day 0 到第二个月的顺序，把每个阶段该做什么、该看哪几个数字写清楚，中间穿插原生家宽与机房段的判定方法，照着排期走，同段连坐的概率会低很多。</p>

<h2>一、Day 0：先把需求盘成一张参数单</h2>
<p>开局别急着询价，先把自己的用量摊开：现有账号多少个、分布在哪些城市、每天活跃时段、是否需要固定本地出口。这几个数字决定了后面是买单条独享还是按段租，也决定了要不要接自建系统。</p>

<h3>算清楚三个数：账号数、并发数、活跃时段</h3>
<p>账号数决定 IP 总量，并发数决定带宽，活跃时段决定晚高峰要不要留冗余。经验值是每条地址对应 1 个账号，并发按账号数的三成估，晚高峰带宽给到白天的 1.8 倍。按这三个数报需求，供应商给的方案才不会过大或过小。</p>

<h3>先定一条硬规则：出口必须是运营商 ASN</h3>
<p>把这条写进需求单，后面所有验收都围绕它。判定方法很直接：拿到地址跑一次 whois，orgname 里出现运营商名字（Comcast、Verizon、AT&amp;T、BT、Deutsche Telekom 之类）算过；出现 Amazon、Google、DigitalOcean、Hetzner、OVH、Vultr 一律算机房段，直接退回。同一个供应商混批的情况很常见，所以要逐条查，不能抽样。</p>

<h2>二、Day 1 到 Day 2：小批量开通与首轮体检</h2>
<p>这两天只做一件事：用最小成本拿到可用样本。建议一次开 10 条，分布到 2 到 3 个城市，不要一次全开同一个地区，否则后面拿不到对比基线。</p>

<h3>开通后 30 分钟内做完四项检查</h3>
<p>第一项查 ASN 与段归属；第二项查地址是否出现在公开的代理名单里，用几个常见的 IP 信誉查询站交叉看；第三项测连通与延迟，同一地址 ping 100 次、curl 20 次；第四项确认出口地区是否与下单城市一致——国家级一致但城市漂移，是低质转售段最典型的特征。</p>

<h3>把每条地址的体检结果落表</h3>
<p>这张表后面每天都要追加一行，是整个测试期最有价值的资产。它同时也是跟供应商沟通的证据，出现争议时不用靠回忆描述现象。</p>

<h2>三、Day 3 到 Day 7：稳定性观察期，重点记同段</h2>
<p>这几天不看开通成功率了，看的是"每条地址背后还有谁"。同段连坐的机制很简单：同一个 /24 里如果有别人在做高强度操作，整段的信誉会一起下降，你什么都没干也会被牵连。</p>

<h3>每天固定两个时段做长连接测试</h3>
<p>建议上午 10 点和晚上 21 点各跑一轮，每轮保持 30 分钟长连接，记录断连次数和重连耗时。住宅线路在晚高峰抖动是正常的，关键是抖完能不能自己恢复。12 小时内断连超过 3 次的地址，标记为待更换。</p>

<h3>用 traceroute 看跳数和出口类型</h3>
<p>真实家宽出口的路径通常跳数多、中间节点杂；机房出口路径干净、跳数少。如果一条自称家宽的地址 traceroute 只有五六跳就出去了，八成是云上转的，值得再核一次 ASN。</p>

<h2>四、第 2 到第 3 周：接进自建系统做批量验收</h2>
<p>到这一步才开始上量。自建系统的价值在于把"开号、分配、记录、回收"串成一条链，出问题时能一眼看到是网络层还是环境层。接之前先确认自己的系统支持按账号维度记录出口，而不是只记一个全局出口。</p>

<h3>压一次 3 倍于日常的并发</h3>
<p>不要等真实高峰来验证。挑一个低峰时段，把并发打到日常的 3 倍，持续 20 分钟，看两件事：错误率是否线性上升、恢复后是否自动回到基线。前者说明带宽不够，后者说明重试策略有问题。</p>

<h3>批量验收看四个指标</h3>
<p>这四个指标建议做成看板，每天扫一眼就够，不用盯实时。</p>

<h2>五、第 2 个月起：扩量、替换与季度复盘</h2>
<p>稳定跑满一个月后，节奏可以放慢，但要建立两条常规动作：一条是替换，一条是复盘。替换解决质量衰减，复盘解决结构问题。</p>

<h3>每月替换比例控制在 10% 以内</h3>
<p>替换太频繁会打断账号连续性，替换太少则会让劣质地址长期占位。做法是给每条地址记一个质量分，按断连次数、延迟偏离、验证提示频率三项打分，月底把最低的 10% 换掉，不用等它彻底坏。</p>

<h3>季度复盘只问三个问题</h3>
<p>同段是否出现集中异常、平均单号成本是升还是降、备用线路是否真的切过一次。第三个问题最容易被忽略——没演练过的备用线路，在真故障时往往切不过去，切一次比看十次配置更有说服力。</p>

<h2>常见问答</h2>

<h3>从开通到能稳定跑，一般要多久？</h3>
<p>答：按上面这条时间轴，两周能看到稳定性结论，一个月能拿到成本数据。想压缩到一周也行，代价是把观察期砍掉，同段问题和晚高峰抖动只能等上线后被动发现，返工成本通常高于多等那七天。</p>

<h3>原生家宽和机房段，肉眼能分辨吗？</h3>
<p>答：能，但要两个证据一起看。一是 whois 的 orgname 和 ASN，运营商名字与云厂商名字区别明显；二是 traceroute 的路径形态。只看其中一个容易误判，因为部分转售平台会把机房地址挂在运营商的子段下。</p>

<h3>同段连坐一定会发生吗？</h3>
<p>答：不一定会，但概率随同段客户数量上升。可控的做法是选卖方自营、同段售出条数有上限的线路，并在合同里写明同段新客户的上架告知义务。完全不承担同段风险的方案基本不存在，只能把概率压低。</p>

<h3>自建系统一定要上吗，用表格记不行吗？</h3>
<p>答：账号在二十个以内，表格加命名规范够用；超过五十个，人工维护的分配表几乎必然出现账号与出口错配，而这类错误排查起来最费时间。判据是"是否需要追溯某条地址上跑过哪些账号"，需要就该上系统。</p>
